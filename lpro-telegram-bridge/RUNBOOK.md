# 運用ランブック（壊れたとき・困ったとき）

この設計の前提は「**Lpro の UI が変わると壊れる。そのとき直すのは `src/config.ts` の SELECTORS と
`src/lpro-adapter.ts` だけ**」。慌てず以下の手順で復旧する。

---

## 0. 送受信が止まった（両方向・まずこれ）

「Telegram に何も来ない」「Telegram で打っても Lpro に入らない」が**両方同時に起きている**ときは、
セレクタ切れ（A章）ではなく **プロセスが止まっている / ログインが切れている / Telegram 側が切れている**
のいずれかであることがほとんど。まず**診断コマンドを1つ**走らせて、どれなのかを確定させる。

```bash
cd lpro-telegram-bridge
npm run triage                       # 既定案件
npm run triage -- --instance=<案件名>  # 追加案件を見るとき
```

**読み取り専用**なので稼働中に実行してよい（DB は readonly で開き、Telegram は `getUpdates` を
呼ばないので本体のポーリングと競合しない。Playwright も起動しないのでプロファイルを奪わない）。

出力は6ブロック。`❌` が付いた行が止まっている原因で、最後の「次にやること」がそのまま復旧手順になる。

| ブロック | 何が分かるか | ❌ のときの行き先 |
|---|---|---|
| 1. 案件と設定 | どの `.env` を見ているか・受信箱とグループID・doctor 相当のチェック | `.env` を直す（案件の取り違えもここで分かる） |
| 2. プロセスの生存 | `bridge.lock`（稼働中は30秒ごとに更新）の鮮度＝**プロセスが生きているか** | E章（`pm2 list` / `pm2 start` / `pm2 logs`） |
| 3. Lpro のログイン | プロファイルの有無・`.lpro-session`（ログイン確認OKのたびに更新）の鮮度・自動ログインの設定有無 | **C章**。`LPRO_LOGIN_ID / LPRO_LOGIN_PASSKEY` があれば自動で入り直す。無い／失敗なら人が画面で入り直す（pm2 restart では直らない） |
| 4. Telegram | トークン有効性(401)・**Webhook が付いていないか**・グループの Topics ON・bot の管理者/トピック管理権限 | B章 |
| 5. 台帳 | **いつから記録が止まっているか**（`seen_messages` の最終記録時刻）・未送信の控えの残り | 止まった時刻が分かればログの該当箇所を見る |
| 6. PM2 ログ | 直近ログから既知の異常（未ログイン / 409 / 401 / chatframe 消失 / 送信失敗 …）を分類・⚠️通知の実文面 | 分類に応じて A / B / C / E 章 |

### よくある確定パターン

- **2 が ❌（プロセス停止）** … PC の再起動後に PM2 が復帰していない、またはクラッシュ連続で PM2 が諦めた。
  → `pm2 list` → `pm2 start ecosystem.config.cjs --only lpro-bridge` → `pm2 save`。
  起動直後に落ちるなら `pm2 logs lpro-bridge` で理由を見る（E章）。
- **2 は OK なのに 5 の最終記録が古い** … ログイン待ちで巡回だけ止まっている典型。
  → 画面のブラウザで Lpro にログインし直す（C章）。`⚠️ Lpro に未ログインです` が Telegram に届いているはず。
- **4 で 409 / Webhook あり** … 同じ Bot トークンで二重起動している（`npm run chatid` の同時実行、
  PM2 に同じ案件が2つ登録、別PCでも起動中 など）。→ どちらか1つに絞る。
- **4 で bot がグループから外れている / 権限落ち** … Telegram 側でグループ設定が触られた。→ B章。

診断で原因が特定できない場合は、**4・5・6 ブロックの出力をそのまま**共有すれば切り分けできる
（会話本文は出力されない。顧客表示名も出さない設計）。

## A. Lpro の画面変更で動かなくなった（最頻ケース）

症状の例:
- ログには出るが Telegram に新着が来ない
- `poll error` が出続ける / `waitForSelector ... Timeout` が出る
- 返信が Lpro に入らない

### 手順

1. **どのセレクタが死んだか切り分ける**
   `HEADLESS=false` で `npm start` し、ブラウザで実際の画面を見る。
   - 「トーク画面（chatframe）が見つかりません」が出続ける → `mainFrame` / `chatFrame`（iframe構造の変化）
     または該当受信箱の talk URL（`CHAT_TALK_URL` = chat_message?method=frame /
     `TALK_TALK_URL` = linechat_message_frame）の変更。どの受信箱で出ているかはログの受信箱名で分かる
   - 顧客行が0件 → `conversationItem`（tr.rowitem）
   - **一覧は取れるのに新着が全く配信されない** → `statusCell` / `unreadText`（未知の状態表記は安全側で未読扱いになる。
     ただし `statusCell` が「返信済」を含む場合のみ未読なし扱いなので、「返信済」の表記が変わった場合は全行が
     未読扱いになり巡回が重くなる。ログの「巡回[チャット応対]: N行/未読M件」/「巡回[ダイレクトトーク応対]: …」で
     気付ける。ログには受信箱名が付くのでどちらの受信箱の話か見分けられる）
   - 顧客が「スキップ」され続ける → `memberIdText`（会員ID要素）
   - 名前が変 → `customerName`
   - メッセージが拾えない → `messageGroup` / `inboundGroupClass` / `bubble` / `msgDatetime`
   - 返信が入らない・「送信を確認できません」→ `replyInput` / `sendButton`
   - そもそもログイン判定で止まる → `loggedInMarker`

2. **新しいセレクタを調べる**
   トーク応対画面で F12 → 該当要素を右クリック → Copy → **Copy selector**（または outerHTML を見てクラス/属性を確認）。

3. **`src/config.ts` の SELECTORS を差し替える**（基本ここだけ）。

4. **行の特定方法が変わった場合**は `src/lpro-adapter.ts` の `findRow()`（会員IDの完全一致で行を特定）を調整。

5. **顧客キー（会員ID）の表示要素が変わった場合**は `src/config.ts` の `SELECTORS.memberIdText` を差し替え。

6. `npm run doctor` で TODO 残りが無いか確認 → `npm start` で再開。

> ヒント: 顧客キーは会員ID（アカバンでも不変）。表示名をキーにしてはならない（同名衝突で取り違える）。

## B. Telegram にトピックが作られない / 送れない

`createForumTopic` が 400 で失敗する場合、コードが下記を促すエラーを出す:

1. グループの **Topics が ON** か
2. bot が**管理者**で「**トピックの管理 (Manage Topics)**」権限を持つか（bot は両グループそれぞれに追加する）
3. 該当受信箱のグループID（`CHAT_GROUP_CHAT_ID` / `TALK_GROUP_CHAT_ID`）が正しいか（`npm run chatid` で取り直す。`-100...` の数値。エラーには受信箱名が付くのでどちらのグループか分かる）

429（レート制限）や 5xx・ネットワーク断は自動でリトライ（指数バックオフ）するので、基本は放置で回復する。
ただし**トピック作成（createForumTopic）だけはネットワーク断・5xx では意図的に再試行しない**
（非冪等のため、応答が届かなかっただけの再試行が重複トピックを生む。429 レート制限のみ
retry_after を待って再試行する）。作成失敗は次の配信サイクルで自然に再試行される。

## B-2. Telegram に出る運用通知（⚠️）の一覧と対処

ブリッジは異常やオペレータ操作の不備を **⚠️ 付きメッセージ**で Telegram に自己申告する。
主なものと対処は以下（詳細は各章参照。重複説明は避けて参照先を示す）。

| 通知の趣旨（文面の要点） | 意味 / 対処 |
|---|---|
| `⚠️ 送信失敗: …` | 返信が Lpro に入らなかった。A章（`replyInput`/`sendButton`）またはセッション失効（C章）を確認。実際は送信済みのこともあるので Lpro で要確認 |
| `⚠️ 前回の停止時に…送信が完了していない可能性` | 停止直前の返信が未送信かもしれない。Lpro で送信済みか確認し、未送信なら送り直す（DBの控えから起動時に通知） |
| `⚠️ このトピックはどの顧客にも紐付いていない…` | ブリッジが作成したトピックでのみ返信できる。手動作成トピックや未紐付けトピックからは Lpro へ届かない |
| `⚠️ 画像・スタンプ等は Lpro へ送信できません`（編集も同様） | Lpro へはテキストのみ送れる。テキストとして送り直す。空メッセージ・編集も反映されない |
| `⚠️ [受信箱] トピック作成に失敗しています…` | B章参照（Topics ON / bot の「トピックの管理」権限 / GROUP_CHAT_ID） |
| `⚠️ 巡回が10回連続で失敗` / `⚠️ 会話の配信失敗が5巡回連続` | セレクタ切れ（A章）かセッション失効（C章）の疑い。ログを確認 |
| `⚠️ [受信箱] 未読顧客がいるのにメッセージを1件も抽出できません` / ブートストラップ0件 | メッセージ系セレクタ切れの疑い（A章）。顧客ゼロなら正常 |
| `⚠️ 未返信の一覧が表示上限に達しました` | 未返信が多すぎて古い顧客を取りこぼす恐れ。Lpro 側で未返信を処理して件数を減らす |
| `⚠️ Lpro に未ログインです…ログイン待機中` | セッション失効（C章）。自動ログインが有効なら文末にその状態（次の再試行時刻・失敗回数）が付く。赤いバナーのブラウザで手動ログインもできる。未ログインが 20 秒（自動ログイン有効時は約 45 秒）続いてから初回、以後 15 分ごと |
| `🔑 Lpro のセッションが切れていたため自動ログインしました` | 自動ログイン（C章）で無人復旧した。対処不要。頻発するなら Lpro 側のセッション寿命が短くなっている（ログで頻度を見る） |
| `⚠️ Lpro の自動ログイン: 自動ログインに失敗しました（n回目）…` | ID/パスキーが拒否された、またはログイン画面の構造が想定と違う。`.env` の `LPRO_LOGIN_ID / LPRO_LOGIN_PASSKEY` を確認。再試行は 30秒→2分→10分→30分→1時間 の間隔（C章）。急ぐなら手動ログイン |
| `⚠️ Lpro の自動ログイン: 送信後にログインフォーム以外のページ…` | 送信後に追加認証や確認画面が出た。表示中のブラウザで続きを人が操作する（15 分は画面を触らない） |
| `🚫 自動ログインを停止しました: 自動ログインしたアカウントがこの案件と一致しません` | `.env` の資格情報が別案件のアカウント（`LPRO_SITE_ID` 不一致）。修正して再起動するまで自動ログインは止まり、手動ログインのみ受け付ける |
| `🚫 Lpro に別のアカウントでログインされていた…` | `LPRO_SITE_ID` と違うサイトでログインされた（別案件への誤送信防止）。自動ログアウト後、この案件のアカウントでログインし直す。即時通知 |
| `✅ Lpro へのログインを確認しました。監視を再開します` | 上の ⚠️/🚫 の解消。⚠️/🚫 を出した場合にだけ届く |

## C. ログインが切れる / 毎回ログインを求められる

- セッションは `USER_DATA_DIR`（既定はプロジェクト直下の `.lpro-profile`）に保存される。**このフォルダを消さない**こと。
- **ブラウザを閉じて開き直すとログアウトになる問題は対処済み（2026-09-11〜）**: Lpro のログインは有効期限なしの
  セッションCookie（`JSESSIONID`）だけで保持され、Chromium は正常終了→再起動でこれを捨てる。ブリッジは
  ログイン確認OKのたびに Lpro の Cookie をデータディレクトリの `.lpro-session`（DPAPI＝ログオンユーザー鍵で暗号化。
  別ユーザー・別PCでは復号不可）に退避し、起動時にプロファイルに無ければ戻す。日次の開き直しはプロセス内で
  直接引き継ぐ。**これにより `pm2 stop`→`start`・PC再起動・日次開き直しでは原則再ログイン不要**
  （Lpro 側でセッションが失効していた場合＝長時間の PC 停止などは従来どおりログイン待ち）。
  起動ログの `Lpro Cookie を復元: JSESSIONID(セッション)（.lpro-session（… 保存））` で引き継ぎの有無が分かる。
  - 退避のタイミング: 「ログイン確認OK」の直後と、ブラウザを閉じる直前（終了処理・再初期化）。内容が前回退避分と同じで
    ファイルも残っていれば書かない（ログ `Lpro Cookie を退避しました（…）` は内容が変わったときだけ出る）。
  - **ログイン待ち中・別アカウント検出中のブラウザの Cookie は退避しない**（ログイン画面が発行した未認証の JSESSIONID で、
    直前まで有効だった退避分を上書きしないため）。
  - `.lpro-session` は **案件ID＋Lpro ホストに束縛**されている（DPAPI の追加エントロピー）。`instances/<案件名>/` を
    フォルダごとコピーして別案件を作っても、コピー先では照合で弾かれ復号もできない（別案件のアカウントに無言でログインしない）。
  - `.lpro-session` を消しても害はない。次の「ログイン確認OK」（巡回中の自己修復時＝おおむね毎時、または再起動後のログイン後）で
    作り直される。消すなら停止中に消すのが確実。
- **Lpro 側のセッション寿命（2026-09-11 時点の理解）**: `JSESSIONID` にクライアント側の期限は無く、ブリッジが巡回している
  限り 2 日以上維持されることを確認済み（2026-09-09〜09-11）。以前「約1時間で失効する」と記録していたが、その観測には
  「ブラウザを閉じて開き直したときに Chromium がセッションCookieを捨てた」ケース（上記で対処済み）が混じっていた可能性が高い。
  サーバー側の失効条件（アイドル時間など）は未確定で、**PC を何時間も止めた／スリープした後は失効していることがある**
  （例: 2026-09-10 朝）。失効すると下記の再ログイン待ちに入り、巡回は一時停止する。
- **自動ログイン（2026-09-17〜）**: `.env` に `LPRO_LOGIN_ID` / `LPRO_LOGIN_PASSKEY`（ログイン画面の ID とパスキー）を
  設定すると、セッション失効でログイン画面になったときにブリッジが自動で入力・送信して復旧する（`src/autologin.ts`）。
  未設定でも、ブラウザのパスワード自動入力でフォームが埋まっていれば送信ボタンだけ自動で押す。`AUTO_LOGIN=off` で無効。
  - 送信は1回ずつ。失敗（マーカーが出ずログイン画面のまま）すると **30秒→2分→10分→30分→1時間** と間隔を延ばして再試行する
    （アカウントロック防止）。その間も表示中のブラウザで手動ログインすれば即復帰する。成功・手動ログインで失敗回数はリセット。
  - 送信後に**ログインフォーム以外のページ**（追加認証・確認画面）になったら失敗に数えず、15 分は画面を触らず人の操作を待つ。
  - 自動ログインで入ったアカウントが `LPRO_SITE_ID` と違う（`.env` の資格情報が別案件）場合は 🚫 を出して**自動ログインを停止**する
    （ログアウト→自動ログイン→別アカウント… の無限ループ防止）。`.env` を直して再起動するまで手動ログインのみ。
  - 通知: 未ログインの ⚠️ を出す前に復旧できたときは `🔑` 1通だけ。⚠️ の後に復旧したときは `✅ …（自動ログインで復旧しました）`。
  - ログの見方: `自動ログイン: 送信しました（.env の資格情報 / メインフレーム / ボタンをクリック）` → `ログイン済みを確認しました`。
    `ログインフォームが見つかりません` が続くときは Lpro 停止中か画面変更（下記）。
  - **ログイン画面の構造が変わって失敗し続けるとき**: ログアウト状態で `npm run dump -- <LPRO_LOGIN_URL> login` を実行し
    `dump/login/frame-*.html` の ID 欄・パスキー欄・送信ボタンを見て `src/config.ts` の `SELECTORS.loginIdInput` /
    `loginPassInput` / `loginSubmit` を確定する（'' は自動判定＝パスキー欄と同じ form 内の直前のテキスト入力／submit ボタン）。
    `test/autologin.test.ts` の模擬ページに同じ構造を足して `npm test` で確認できる。
- 巡回中に切れた場合は poll エラー時に自動で再ログイン待ち（`ensureLoggedIn`）に入る。
  ログイン画面へリダイレクトされるとトーク画面（`chatframe`）が表示されなくなるため、
  エラー化して同じ復旧経路に入る。画面が見える状態（`HEADLESS=false`）なら手動で通せば復帰する。
- **自動ログインが無効・失敗のときは、再ログインは人が headed ブラウザ上で行う**（プロセスは生きたまま
  ログイン待ちで止まるだけなので、`pm2 restart` では解決しない）。表示中のブラウザでログインすれば巡回が再開する。
- 2FA は初回だけ手動。確立後に `HEADLESS=true` で弾かれるなら headed のまま運用する。

## D. 新着がダブる / 過去ログが大量に流れる / 新着が来ない

- 本実装は **フィンガープリント方式**(2026-07-11 実DOM確定時に件数ベースから移行):
  メッセージごとに「会員ID+日時+本文」のハッシュを `seen_messages` テーブル(bridge.db)に記録し、
  **台帳に無いハッシュのメッセージだけ**配信する。Lpro の履歴窓(行内に直近数件のみ表示)が
  どうずれても、同数入れ替わりでも、取りこぼし・再配信は起きない設計。
- 送信は1件成功ごとに既知化するので途中失敗でも重複しない
  (例外: 4000字超の長文は分割送信されるため、分割の途中で失敗した場合のみ先頭部分が重複し得る)。
- **自分側（L-Pro 側）の発言は「追記ブロック」に編集で載せる（`MIRROR_SELF=silent`・2026-09-11〜）**: Telegram は新しい
  メッセージを投稿すると必ず未読（バッジ）が増えるが、既存メッセージの編集は未読も通知も発生させない。そこで
  一斉配信・自動応答・PC直返信は新規投稿せず、トピック内の1つのメッセージ「🔷 L-Pro側（配信・返信）」へ編集で追記する。
  顧客の発言を届けた直後に空の追記ブロック（見出しに顧客発言の抜粋付き）をサイレントで添えるので、以後の配信は
  何回来てもバッジを増やさない。**鳴る・バッジが増えるのは顧客の発言のときだけ**（そのとき未読は顧客の発言＋空ブロックの
  2つ付くが、同時なので開けば両方消える。トピック一覧のプレビューは「🔷 … ← 「顧客発言の抜粋」」の行になる）。
  トピックを開けば前後のやり取りが時系列で読める。例外的にサイレントの未読が1つ増えるのは、追記ブロックが無い顧客に
  初めて自分側の発言が来たとき（導入直後の既存トピック）、ブロックが上限（約3800字）を超えて次のブロックを作るとき、
  Telegram から返信した後の最初の L-Pro 側発言（返信の下に新しいブロックを作る）。初遭遇（履歴一括）は従来どおり
  連結チャンクで流し（429 対策）、末尾に空ブロックを添える。自分側の追記に失敗しても顧客側の配信は止めない
  （自分側は次サイクルで再試行）。`MIRROR_SELF=notify` で従来どおり通知付きの通常
  メッセージ、`off` で自分側を流さない（ブリッジが読んだ分は既読台帳に記録するので、後で戻してもその分が一斉に
  流れることはない）。切り替えは案件の `.env` を変えて再起動。
- それでもダブる場合: 同一顧客で **日時表示や本文の描画が変わる**とハッシュが変わる。
  `.mmsgdt` の中身が変化していないか(A-1 の `msgDatetime`)を確認。
- 新着が来ない場合: `statusCell`/`unreadText`(未返信判定)を確認。`ONLY_UNREAD=false` にすると
  全行を毎回読むので、未返信判定が壊れていても届くようになる(重い・既読台帳があるので安全)。
  なお受信箱は2つ(チャット応対/ダイレクトトーク応対)あり、どちらの巡回の話かはログの
  「巡回[受信箱名]: N行/未読M件」で見分けられる。片方だけ来ない場合は、その受信箱の
  `*_TALK_URL`/`*_GROUP_CHAT_ID` が両方設定されて有効になっているか(`npm run doctor`)も確認する。
- 顧客1人に**トピックが複数できる**ことは起きない設計(キー=会員ID固定)。起きたら `memberIdText` を確認。
- 配信判定そのものは `src/logic.ts`(`decideDeliveryBySeen`)に分離済み。挙動を変えるときは
  まず `test/logic.test.ts` にケースを足してから直すと安全。
- 既定の `ONLY_UNREAD=true` は「未返信」状態の顧客だけを読む。顧客の新着に Lpro の画面から
  直接返信すると状態が「返信済み」に変わり、そのメッセージは Telegram のトピックに現れないことがある
  （業務上は返信済みなので実害は小さい）。Telegram 側にも完全なミラーが必要な運用では
  `ONLY_UNREAD=false`（全行を毎巡回チェック。台帳があるので重複はしない）を使う。

## E. プロセスが落ちる / 常時起動

> **現状（2026-07-14）: PM2 常駐化は実施済み。** `pm2 start ecosystem.config.cjs` で
> `lpro-bridge` が online。logrotate 設定・ログオン時自動復帰まで登録済み（下記各項）。

- **⚠️ Lpro セッションの失効（無人運用の最大の制約）**: Lpro のログインセッションは、ブリッジが巡回している限り
  維持される（2日以上を確認）が、**PC の長時間停止・スリープの後などにサーバー側で失効している**ことがある
  （以前「約1時間で失効」と書いていたのは、ブラウザ開き直し時の Cookie 破棄が混じった観測。C章参照）。
  ブリッジは失効を検知すると poll エラー経路から「未ログイン」状態に入る。**`LPRO_LOGIN_ID / LPRO_LOGIN_PASSKEY` を
  設定していれば自動ログインで無人復旧する（2026-09-17〜。C章）**。未設定・失敗時は headed ブラウザで手動ログイン待ちになる
  （巡回はその間停止する。Telegram に `⚠️ Lpro に未ログインです` が届く）。画面が見えていればそこで再ログインすれば復帰する
  （プロセスが落ちるのではなく、ログイン待ちで止まる）。ブラウザ開き直し・PM2 再起動・PC 再起動だけなら
  2026-09-11 以降は Cookie を引き継ぐので再ログイン不要（C章）。長時間放置すると新着が届かなくなる点を運用者が把握しておくこと。

- PM2 の基本操作（実際に使ったコマンド）:
  - `pm2 start ecosystem.config.cjs --only lpro-bridge` … 起動（常駐開始）。**引数なしは全案件を再起動する**ので使わない（G章）
  - `pm2 logs lpro-bridge` … ログを追う
  - `pm2 restart lpro-bridge` … 再起動 / `pm2 stop lpro-bridge` … 停止
  - `pm2 save` … 現在のプロセス一覧を保存（自動復帰の対象にする。設定変更後は必ず実行）
  クラッシュ時は5秒後に自動再起動（30秒以内に連続クラッシュが続くと停止）。
  node + tsx で直接起動する構成のため Windows でも動く（`pm2 start npm -- start` は不可）。
- **終了処理の実際**: Ctrl+C（コンソール実行時）では実行中の返信送信を待ってから（最大20+5秒）
  bot・ブラウザ・DB を正しく閉じる。2回目の Ctrl+C は強制終了。
  PM2 経由の停止は `shutdown_with_message: true` により（OS を問わず）シグナルの代わりに
  'shutdown' IPC メッセージが送られ、index.ts の `process.on('message')` が終了処理を起動する
  （`kill_timeout` 40秒を超えると強制kill）。強制killでも SQLite は WAL のおかげで
  通常は壊れない。chromium のプロファイルロック問題が出た場合、Windows ではロックは
  プロセス生存に紐づくミューテックスなので、タスクマネージャで残った chromium を終了すれば
  解消する（Linux/macOS のような `Singleton*` ファイル削除は Windows では不要・存在しない）。
- **OS起動時の自動立ち上げ（Windows）: 登録済み**。`pm2 startup` は Windows 非対応のため、
  `pm2-windows-startup`（`npm i -g pm2-windows-startup` → `pm2-startup install`）で
  HKCU の Run キーに登録し、ログオン時に `pm2 resurrect` で保存済みプロセス（= `pm2 save` した状態）
  を自動復帰させる構成にしてある。プロセス構成を変えたら `pm2 save` を忘れずに。
  headed ブラウザを使うため、復帰にはログオン済みデスクトップセッションが必要
  （完全無人にするなら自動ログオン設定を検討。後述のセッション失効の項も参照）。
- Telegram のポーリングが 401（トークン失効）/ 409（多重起動）で止まった場合は
  半死にで放置せず、プロセスを終了コード1で落として PM2 に再起動させる設計。
  409 が続くなら `npm run chatid` や別の `npm start` が同時に動いていないか確認。
- **PM2 で起動直後にクラッシュを繰り返す**とき: `pm2 logs lpro-bridge` で
  「環境変数 ○○ が未設定です」が出ていないか確認（.env の記入漏れ。`npm run doctor` で全項目確認できる）。
- **ログの取り扱い**: PM2 のログは**平文**で蓄積される（リポジトリ外・.gitignore の保護対象外）。
  実パスは以下:
  - `C:\Users\masay\.pm2\logs\lpro-bridge-out.log`（標準出力）
  - `C:\Users\masay\.pm2\logs\lpro-bridge-error.log`（エラー）
  - 追加案件は `lpro-bridge-<案件名>-out.log` / `-error.log`（案件ごとに別ファイル）
  ブリッジは会話本文をログに出さない方針だが、顧客表示名は運用ログに含まれる。
  ローテーションは `pm2 install pm2-logrotate` で**設定済み**（1ファイル 10MB 上限 / 30世代保持 / 圧縮）。
  無期限に肥大化することはない。
- 強制終了して `bridge.db-wal` / `.lpro-profile` が壊れた疑いがあるとき:
  - `.lpro-profile` を消すと**再ログインが必要**（消すのは最終手段）。
  - `bridge.db` を消すと**全顧客が初回ブートストラップ扱い**になり、既存トピックとの紐付けが切れる。原則消さない。
  - `CHAT_GROUP_CHAT_ID` / `TALK_GROUP_CHAT_ID` を変更すると、起動時に**受信箱ごとに変更を検知**し、
    その受信箱の旧グループに紐付いたトピックだけを自動リセット（`clearTopicsByGroup`）して、
    次回配信時に新グループへ作り直す（旧グループのトピックはそのまま残る。もう一方の受信箱のトピックは影響を受けない）。

## G. 案件（Lproアカウント）を追加する

案件＝「Lpro アカウント1つ × Telegram Bot 1つ × グループ2つ」。案件ごとにプロセス（PM2 アプリ）と
データ（instances/<案件名>/ 配下の .env / .lpro-profile / bridge.db / backups）を完全に分ける。
既定案件（最初の案件）はルート配置のまま（アプリ名 `lpro-bridge`）。

### 事前に用意するもの（担当者）

| 種別 | 内容 |
|---|---|
| Lpro | ログインページURL（例 `https://lpro-pmN.com/manage/`）／/manage のベーシック認証 ID・パスワード／チャット応対URL（`.../manage/chat_message?method=frame`）／ダイレクトトーク応対URL（`.../manage/linechat_message_frame`）／Lpro のログインID・パスワード（初回ログイン時に人が入力。ブリッジには保存しない） |
| Telegram Bot | BotFather で **新しい Bot** を作りトークンを控える（既存案件の Bot は使い回さない） |
| Telegram グループ | 案件用にグループを **2つ**（チャット応対用／ダイレクトトーク応対用）作成 → 「トピック」を ON → 新 Bot を **管理者（トピックの管理）** で追加 |

### 手順（PC 側）

```powershell
cd C:\Users\masay\compensation-manual\lpro-telegram-bridge
mkdir instances\<案件名>                              # 英数字・-・_ のみ（例: foo）
copy .env.example instances\<案件名>\.env             # 開いて記入（INSTANCE_LABEL=表示名、トークン、Lpro のURL/認証）
npm run doctor -- --instance=<案件名>                  # 抜け・他案件との競合（同じトークン/グループ等）を検出
npm run chatid -- --instance=<案件名>                  # 新 Bot で各グループにメッセージ → chat.id を .env に記入 → Ctrl+C
npm run doctor -- --instance=<案件名>                  # もう一度 [OK] を確認
npm run login  -- --instance=<案件名>                  # 開いたブラウザで Lpro にログイン（プロファイルに保存）→ Ctrl+C
pm2 start ecosystem.config.cjs --only lpro-bridge-<案件名>
pm2 logs lpro-bridge-<案件名>                          # 「巡回開始」を確認
pm2 save                                              # ★必須★ 次回ログオン時の自動復帰に含める
```

- 案件名は**フォルダ名と大文字小文字まで同じ**に打つ（PM2 アプリ名・ログ名にもそのまま使われる）。
- `npm run chatid` はその案件の Bot トークンだけで待ち受けるので、他案件の本体が稼働中でも安全（別 Bot）。
  ただし同じ案件の本体が動いている状態では実行しない（409）。
- 初回ログイン後、ログに `Lpro サイト確認: site_id=NN（表示名）` が出る。その NN を `.env` の `LPRO_SITE_ID` に記入して
  `pm2 restart lpro-bridge-<案件名>`。以後、**別のアカウントでログインされると自動でログアウトして正しいログインを待つ**
  （同じ Lpro サーバーに複数案件があるときの、別案件の顧客への誤送信防止。既定案件は `LPRO_SITE_ID=16` 設定済み）。
- **競合の効き方（非対称）**: 追加案件の `.env` が他案件と同じ Bot トークン／グループ／プロファイル／DB を指していると、
  **追加案件側が起動を拒否**する（`⚠️ 起動前チェックに失敗` が Telegram に届く）。既定案件（ひかり）は止めず、警告を
  Telegram に出して稼働を続ける。作りかけ・コピーしただけの `instances/<案件名>/.env` を放置しない。
- 一時的に外す／準備中にしておく: `pm2 delete lpro-bridge-<案件名>` → `pm2 save`（PM2 に登録済みのアプリはファイルを
  改名してもログオン時に起動されるため、必ず PM2 からも外す）＋ `instances/<案件名>/.env` を `.env.disabled` に改名
  （ecosystem の一覧・競合チェックの両方から外れる）。**稼働中の `.env` を別案件のテンプレートにコピーしない**
  （Bot・グループが同じままだと競合になる）。**`instances/<案件名>/` をフォルダごとコピーして別案件を作らない**
  （`.lpro-profile` と `.lpro-session` にログイン状態が入っている。`.lpro-session` は案件ID・ホストに束縛されているので
  コピー先では復元されないが、コピーしてしまった場合は両方を削除してから `npm run login` する）。
- 既定案件（ひかり）の再起動時に「稼働中の案件（bridge.lock が2分以内に更新されている案件）」と Bot/グループ/フォルダが
  重なっていれば、既定案件も起動を拒否する（`⚠️ 起動前チェックに失敗` 通知）。相手が止まっているときは警告のみで稼働継続。
- 起動前チェック失敗の Telegram 通知は、その案件の Bot トークンとグループが有効なときだけ届く（トークン未設定などの
  作りかけでは届かない）。届かないときは `pm2 logs lpro-bridge-<案件名>` を見る。
- **シェルで `BRIDGE_INSTANCE` を手動設定しない**。PM2 は起動時にシェルの環境変数を丸ごと取り込むため、その状態で
  `pm2 start ecosystem.config.cjs` / `pm2 restart --update-env` を打つと既定案件が別案件として立ち上がる。
  起動時に「PM2 アプリ名と案件が一致しません」で止まる安全弁はあるが、起動自体が止まる。案件の指定は必ず `--instance=`（CLI）か
  `ecosystem.config.cjs`（PM2）に任せる。
- 引数なしの `pm2 start ecosystem.config.cjs` は稼働中の案件まで再起動してしまう。追加は必ず `--only`。
- 停止／撤去: `pm2 stop lpro-bridge-<案件名>`／`pm2 delete lpro-bridge-<案件名>` → `pm2 save`。データは instances/<案件名>/ に残る。
- 通知は `[表示名]` 付きで届く。ログイン待ちのウィンドウには赤いバナー「【表示名】このウィンドウで Lpro にログインしてください」が
  出るので、案件が複数あってもどのウィンドウでログインすべきか取り違えない。
- リソース目安: 1案件あたり node 約 0.7GB ＋ chromium 約 0.8GB（32GB 機なら数案件は余裕）。
- **未検証**: 同じ Lpro アカウント（同じログイン）を2案件で使う構成（Lpro が同時セッションを許すか不明。片方のログインが他方を失効させる恐れ）。
  案件＝別アカウントを前提にする。

### 日次のブラウザ再起動（2026-09-07〜）

長時間稼働で「一覧に行が1件もありません」「検索フォームが現れません」などの一過性エラーが日を追って増える
傾向が観測されたため（2期間で再現。9日目に初日の約7倍）、毎朝の日次ティック（💓）の `DAILY_RECYCLE_DELAY_MIN`
分後（既定10分＝9:10）にブラウザを閉じて開き直す。毎時0〜7分台は Lpro 側の一過性エラーが集中する時間帯なので、
そこを避けて開き直す。`DAILY_BROWSER_RECYCLE=false` で無効化できる。💓には「一覧取得失敗 N 回 / 会話処理失敗 N 回」
も載るので、傾向が戻らない場合はこの数字で気付ける。

**ログインは自動で引き継ぐ（2026-09-11〜）**: Lpro のログインは有効期限なしのセッションCookie（`JSESSIONID`）だけで
保持されており、Chromium は「正常終了→次回起動」でセッションCookieを捨てる（実験で確認。9/11 の定期再起動で
ログアウト→ログイン待ちになった原因）。そのため開き直しの前後で Cookie を明示的に引き継ぐ（`src/session.ts`）。
ログに `開き直し前に Lpro Cookie を退避: JSESSIONID(セッション)` → `Lpro Cookie を復元: …（開き直し前の退避分）`
→ `Lpro ログイン確認OK` と並べば正常。Lpro 側でセッションが失効していた場合だけ従来どおりログイン待ちに入る。
