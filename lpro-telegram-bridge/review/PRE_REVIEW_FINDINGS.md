## 棄却された指摘（検証で反証済み・再調査不要の参考）

- (core-logic) Second Ctrl+C cannot force exit if shutdown hangs — 反証: The re-entry guard in shutdown() (src/index.ts:68) is indeed a no-op on a second SIGINT, but the claimed user-facing scenario cannot occur because the app's handler is not the only one. initBrowser() (src/lpro-adapter.ts:11) launches chromium without handleSIGINT:false, and Playwright's default handleSIGINT:true installs its own process-level SIGINT handler in the same Node process (playwright-core runs in-process: node_modules/playwright-core/index.js exports coreBundle.inprocess.playwright; handler at coreBundle.js sigintHandler, lines ~8714-8731). Node invokes all SIGINT listeners, so: on the FIRST Ctrl+C Playwright gracefully closes the browser and then calls process.exit(130) — the process exits even if stopBot() is hung on a network outage; on the SECOND Ctrl+C (sigintHandlerCalled already true) Playwright synchronously force-kills the chromium process tree (SIGKILL / taskkill on win32) and calls process.exit(130) immediately — exactly the force-exit the fixHint requests, covering the 'unresponsive chromium' case too. Playwright's handler is only removed after the browser process has exited, at which point shutdown() has nothing left but synchronous closeDb() + process.exit(0), so no hang window remains. The residual corner case (chromium already dead before Ctrl+C AND stopBot stalls) is bounded, not indefinite: grammY 1.30's bot.stop() aborts the in-flight getUpdates via pollingAbortController.abort() (node_modules/grammy/out/bot.js:338-347) and its single offset-confirming getUpdates fails within the ApiClient's bounded request timeout. 'Repeated Ctrl+C does nothing, must kill from Task Manager' is therefore refuted. (The actual defect in this area is the opposite: Playwright's first-SIGINT process.exit(130) can preempt the app's stopBot()/closeDb() cleanup — a different finding.)
- (telegram) Topic name over 128 chars fails with a 400 that gets misdiagnosed by the friendly error message — 反証: The over-128-char scenario cannot occur. The topic name passed to createForumTopic (telegram.ts:39, `name || customerKey`) comes exclusively from pollConversations() in lpro-adapter.ts, where line 56 caps it: `const name = nameText.slice(0, 60)` — max 60 UTF-16 units, always under Telegram's 128 limit no matter how long the real LINE display name or row text is after the selector TODOs are filled. The `customerKey` fallback only triggers when name is the empty string, and in that branch customerKey is either the short id attribute (idAttr) or the same empty string (line 55: `idAttr ?? nameText`) — a row-text-derived key longer than 128 chars is impossible there because non-empty row text would have produced a non-empty name, making the fallback unreachable. The only real 400 risk from this expression is an EMPTY name (both nameText empty and idAttr null), which is a different defect than the one reported. Also, the wrapped 400 message already includes `詳細: ${e.description}`, so the true Telegram description would not be hidden.
