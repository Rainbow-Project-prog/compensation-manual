## 6. 実DOM確定に伴うアダプタ全面改修とその検証（2026-07-11・23エージェント / Opus 4.8）

`npm run dump` で実DOM（chatframe・顧客100行）を取得し、SELECTORS 確定＋アダプタ全面改修
（フィンガープリント[22]・送信検証[25]・行同一性照合[19派生]・非テキスト対応）を実装。
改修差分への敵対的検証で **確定7 / 保留1 / 棄却1** → 全て対処:

- **high: 実DOMのメッセージは新→旧順**（全100行で確認）→ readInbound を時系列昇順に統一。
  放置すると初遭遇時に最新メッセージを既読化だけして恒久喪失＋配信が逆順になっていた
- **high×2: bootstrap 経路の事前一括既知化** → 「配信しない過去ログ」だけを事前既知化し、
  配信対象は1件成功ごとに既知化する方式へ（途中失敗は次巡回の未知差分が再配信）
- 返信後の即時取り込み前に画面を開き直す（送信操作がフレームを再読込するとは限らない）
- 送信検証に第3シグナル「送った本文を含む自分側吹き出しの増加」を追加し、
  どのシグナルで成功判定したかをログ出力（実機初送信テストで挙動確定する）
- 未読判定を安全側に変更: 「未返信」を含む **or** 「返信済」を含まない状態は未読扱い
  （dump 時点で未返信行が0件で実表記が未検証のため。誤判定しても台帳があるので重複配信なし）
  ＋ 巡回ごとの行数/未読数を変化時にログ（未読0件が続く無音障害の観測用）
- 同分・同文連投の窓ズレによる連番衝突（抑止方向・稀）をコード内コメントで文書化

## 7. デプロイ直前の最終総点検（2026-07-12・51エージェント / Opus 4.8）

全コード・設定・ドキュメントを対象に6レンズ監査＋敵対的検証＋最終ゲート判定を実施。
**確定21件（コード8・ドキュメント13）→ 全対処。ゲート判定 = go-with-conditions**
（コード自体は健全。ただし送信検証シグナル・未返信の実表記・bot権限はコードでは確定できないため、
テスト顧客での段階的実機テストを通過するまで実顧客への返信運用は解禁しない）。

コード側の主な対処:
- **high: 未送信返信の無音消失（非graceful終了時）** → 返信を送信前に `pending_replies` テーブルへ
  永続化し、送信成功/失敗通知後に削除。再起動時に残っていれば該当トピックへ「未送信の可能性」を
  通知（自動再送はしない=二重送信防止）。uncaughtException も排水（最大8秒）してから終了
- **high: 旧形式DB持ち越し時の一斉再配信** → `fp_seeded` メタで検出し全顧客を再ブートストラップ
- **medium×2: 無音障害の自己申告不足** → トピック作成失敗の即時通知（1時間スロットル）、
  会話単位の配信失敗5巡回連続の通知、未読ありなのに抽出0件が10巡回続いた場合の通知を追加
- low: 台帳の200日プルーニング（年欠落ハッシュの年跨ぎ衝突予防）/ 真の新規顧客のバースト連投は
  窓全件配信（bootstrapTail で切らない）/ sendMessage 再試行の重複許容方針をコメントで明文化
- ドキュメント13件: 改修前の記述（件数ベース・SELECTORS未確定・旧セレクタ名・手順）を全て現状に同期

最終ゲートの実機チェックリスト（8段階）は本ファイル末尾ではなくデプロイ手順として運用する:
段階0 クリーン確認 → 段階1 ログインのみ → 段階2 テスト顧客受信・未読判定 → 段階3 テスト顧客送信
（送信シグナル確認・一括送信不発火確認）→ 段階4 実顧客カナリア監視 → 段階5 PM2 graceful停止・クラッシュ復帰。

**既知残余として文書化（[22] フィンガープリント移行で解消予定）**:
- 停止中に届いたが**未読バッジが立っていない**メッセージは、再起動時のブートストラップで
  既読基準化され配信されない（未読付きは巡回の tail 配信で救済済み）
- 巡回・返信の全体直列化により、Telegram の 429 リトライ待ち（最大60秒）中は
  他の会話の取り込み・返信も待たされる（正しさ優先のトレードオフ）
